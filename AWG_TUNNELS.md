# Туннель между панелями и выборочный маршрут AI + TikTok

У существующего сервера AWG 2 или AWG 3 можно подключить выход через второй сервер. Входящий сервер сохраняет свой адрес, порт, ключи, параметры AWG и клиентов. Для выхода создаётся отдельный интерфейс с параметрами из импортированного клиентского конфига. Версии входа и выхода независимы: например, клиент AWG 2 может подключаться к первому серверу, а второй участок работать по AWG 3.

## Подключение к работающему серверу

1. На втором сервере создайте отдельного клиента для первого сервера. Не используйте этот клиентский профиль одновременно на другом устройстве.
2. Скачайте его полный конфиг. Нужны `[Interface]`, `[Peer]`, ключи, адрес клиента, endpoint и все параметры AWG. Для AWG 3 сюда относятся ключи защиты заголовков и параметры padding; копировать только старые `Jc` / `H1` недостаточно.
3. На первом сервере откройте настройку туннеля в карточке уже существующего сервера и вставьте конфиг второго сервера.
4. Выберите режим маршрутизации и поведение при недоступности второго сервера, затем сохраните.
5. Проверьте соединение клиента и появление handshake с обеих сторон.

Менять пользовательские профили AWG при добавлении или отключении выходного туннеля не требуется. Изменение маршрута может оборвать уже открытые интернет-соединения; приложения установят их заново. Если первый сервер остановлен, настройка сохраняется и применяется при его запуске.

При замене второго сервера используйте новый полный клиентский конфиг. При отключении туннеля сервер возвращается к обычному выходу через свой сетевой адаптер. Клиент на втором сервере остаётся в его панели: удаляйте его отдельно, когда он больше не нужен.

Если применение настройки завершается ошибкой, панель восстанавливает предыдущий конфиг и маршрут. Если восстановление тоже не удалось, она сообщает об этом и оставляет трафик заблокированным; после исправления причины остановите и заново запустите этот сервер в панели.

## Режимы маршрутизации

| Режим | Через второй сервер | Через обычный выход первого сервера |
| --- | --- | --- |
| Весь трафик | Весь клиентский интернет-трафик | Служебное соединение самого туннеля |
| Российские IP напрямую | Адреса вне загруженного списка российских сетей | Российские IP из списка |
| Selected services | Выбранные ChatGPT, Codex, Claude и/или TikTok | YouTube и остальные назначения |
| AI + TikTok, Standard | Адреса выбранных AI-сервисов и TikTok | Остальные назначения |
| AI + TikTok, Maximum coverage | Адреса выбранных сервисов и широкие сети общих CDN / облачных провайдеров | Назначения вне этих сетей |

Режим AI + TikTok использует список доменов в `web-ui/routing_policy.py`, включая ChatGPT / OpenAI / Codex, Claude / Anthropic и TikTok. Поддомены также учитываются. Список можно расширить в этом файле и пересобрать контейнер.

Для AWG используются несколько источников адресов:

- **DNS клиентов.** Панель перехватывает обычные запросы по UDP и TCP на порту 53. Отдельный локальный DNS-процесс получает IPv4 выбранных доменов и добавляет их в набор маршрутизации до выдачи ответа клиенту.
- **Предварительное разрешение известных имён.** Сервер самостоятельно получает IPv4 основных хостов ChatGPT, OpenAI, Claude и TikTok через DNS-over-HTTPS Google. Обновление выполняется каждые 10 минут; найденные адреса сохраняются на час. Первый запуск обновления выполняется фоновым работником, без ожидания первого запроса клиента. При частичной ошибке DNS или отсутствии адресов повторная попытка выполняется примерно через минуту; предыдущие ещё не истёкшие адреса сохраняются. После успешного обновления возвращается обычный интервал 10 минут. Это помогает при клиентском DNS-кэше и части запросов через защищённый DNS, но не гарантирует совпадение с любым ответом, полученным клиентом.
- **Опубликованные сети и ваши дополнения.** Встроен входящий диапазон **API и Console Anthropic `160.79.104.0/23`**. Он не представляет весь веб-сайт Claude и его CDN. В настройках туннеля можно добавить другие проверенные публичные IPv4 или CIDR.

Изученные клиентские DNS-адреса сохраняются примерно раз в 30 секунд и восстанавливаются после пересоздания контейнера, пока не истёк их срок. Предварительно найденные адреса также сохраняются в каталоге данных панели. Правила применяются к конкретному входящему AWG-интерфейсу; другие серверы и собственный трафик хоста не получают его политику.

Списки доменов и известных хостов находятся в `web-ui/routing_policy.py`. Они расширяют покрытие, но не являются полным перечнем всех будущих адресов сервисов. Для полного статического списка ChatGPT/Codex и TikTok нет подтверждённого источника, гарантирующего покрытие приложений. В профиле **Standard** широкие сети общих провайдеров не добавляются. Для избыточного покрытия предусмотрен отдельный профиль **Maximum coverage**.

Для VLESS выбор производится по домену в правилах Xray; HTTP / TLS / QUIC sniffing помогает определить домен, когда клиент передал только IP. Выбранные соединения получают отдельную метку и выходят через AWG-туннель. Xray и панель должны разделять сетевое пространство, как в штатном `docker-compose.yml`.

## Выбор отдельных сервисов: YouTube локально

Для точного выбора сервисов откройте **Manage tunnel → Routing mode → Selected services (domains; YouTube stays local)**. Отметьте **ChatGPT**, **Codex**, **Claude**, **TikTok** и сохраните. При первом выборе отмечены все четыре; можно снять любые флажки, включая все — тогда всё выходит локально. После смены режима переподключите VPN и полностью перезапустите приложения, чтобы обновились соединения и DNS-кэш. Удалять туннель, сервер или клиентов не требуется.

Этот режим не использует широкие подсети облаков и не применяет поле дополнительных CIDR. Старые **AI + TikTok / Standard / Maximum coverage**, **All traffic** и **Russian IPs local** остаются доступными; их параметры сохраняются при переключении. Само обновление проекта не переводит существующие серверы в новый режим.

Для AWG применяется отдельный процесс **sing-box 1.14.3-awg-domain1** на каждый входящий сервер. Он получает TCP/UDP после расшифровки AWG, перехватывает обычный DNS и выдаёт выбранным доменам отдельные виртуальные IPv4 (FakeIP). Поэтому два сервиса на одном реальном IP сохраняют разные доменные правила: выбранный ChatGPT может выйти через Европу, а YouTube — через первый сервер. HTTP Host, TLS SNI и QUIC sniffing помогают распознать соединения с реальными адресами из старого DNS-кэша. Видеопотоки `googlevideo.com`, страницы и остальные домены YouTube имеют приоритетный локальный маршрут. Неопознанные назначения выходят локально. Содержимое HTTPS не расшифровывается, сертификат на телефон устанавливать не нужно.

Локальный трафик действительно выходит через обычный интерфейс первой VPS. Выбранные соединения и DNS-разрешение их реальных адресов получают метку существующего AWG-туннеля. DNS для обычных доменов использует локальный выход. Используется Cloudflare DNS-over-HTTPS; доступность этого резолвера нужна соответственно с первого и выходного сервера. Никаких новых публичных портов Docker открывать не требуется. Прозрачный обработчик доступен только трафику соответствующего AWG-интерфейса; другие серверы панели сохраняют свои маршруты.

В сборку включено небольшое исправление сохранения FakeIP в sing-box: счётчик адресов сохраняется синхронно, а чтение метаданных не удаляет их. Это проверяется немедленной принудительной остановкой и повторным запуском без нового DNS-запроса. Исходное исправление находится в `scripts/patch_sing_box_fakeip.py`.

База FakeIP хранится в `/etc/amnezia/routing/domain-<table>.db` и сохраняется при пересоздании контейнера вместе с остальными данными. При смене списка сервисов процесс перезапускается и открытые соединения могут оборваться; соответствия адресов сохраняются. При аварийной остановке процесса захватывающие правила остаются, а фоновая проверка восстанавливает процесс. Если конфигурация не проходит проверку, панель откатывает изменение. Во время запуска, остановки и изменения маршрута оба пути обработки трафика защищены временными правилами.

Для VLESS используются те же списки сервисов непосредственно в Xray: сначала локальные домены YouTube, затем выбранные сервисы, затем локальный маршрут по умолчанию. Новый процесс sing-box для такого входа не нужен. Как и раньше, распознавание зависит от домена, переданного клиентом или доступного для sniffing.

Ограничения и особенности:

- ChatGPT и Codex используют общие домены OpenAI, включая `chatgpt.com`. Выбор любого из них включает общие узлы обоих продуктов; отличить зашифрованные URL внутри одного домена нельзя. Gemini и другие AI-сервисы прежнего режима сюда не включены.
- Используйте DNS через VPN. **Private DNS / DoH / DoT**, зашифрованный ClientHello (ECH) вместе с независимым DNS, нестандартные протоколы и неизвестные адреса без доменного имени могут не распознаться и выйти локально. GeoSite — список правил, а не гарантия распознавания любого приложения. Перехватывается обычный DNS TCP/UDP 53; защищённый DNS не блокируется автоматически.
- Для ChatGPT Voice добавлены только опубликованные OpenAI отдельные IPv4 на UDP 3478. Это узкое исключение для STUN без имени сервиса, не сети общего облачного провайдера. Некоторые точные узлы авторизации/проверки устройства общие с другими приложениями и тоже могут пойти через туннель.
- Режим рассчитан на существующие IPv4-профили AWG. Перехваченные AAAA-запросы получают пустой ответ; HTTPS/SVCB-подсказки подавляются только для выбранных сервисов, чтобы реальный адрес не обходил FakeIP. IPv6 вне VPN по-прежнему нужно настраивать отдельно. Сеть `198.18.0.0/15` зарезервирована под FakeIP; пересекающиеся с ней адреса входа или туннеля отклоняются.
- При **fail_close** распознанные сервисы блокируются, если выходной туннель пропал, а YouTube продолжает использовать первый сервер. При **fail_open** выбранные сервисы временно выходят локально. Это не устраняет ограничения самого сервиса для IP европейской VPS.
- Диагностика в панели показывает решение доменного правила и проверяет процесс/правила маршрутизации. Проверка одного общего IP без домена отображается как неизвестная; она не выдаётся за фактический маршрут приложения.

Списки GeoSite зафиксированы в сборке от 2026-10-20, работают офлайн и обновляются вместе с проектом. Источники, лицензия, версия и точечные дополнения описаны в `web-ui/data/service_domains/SOURCES.md`. Архитектура опирается на [доменное разделение Karing](https://karing.app/ru/tutorial/diversion), [DNS Karing](https://karing.app/ru/app-manual/dns) и [постоянный FakeIP-кэш sing-box](https://sing-box.sagernet.org/configuration/experimental/cache-file/).

Обновление совместимо с существующим каталогом `/etc/amnezia`, клиентами, ключами, настройками AWG и старой маршрутизацией. Сохраните свой `.env`, локальные изменения `docker-compose.yml` (особенно HTTP/UDP-порты и пути томов) и резервную копию `/etc/amnezia`. Затем обновите исходники и пересоберите контейнеры обычным `docker compose up -d --build --force-recreate`. Новый режим включается отдельно в настройках туннеля.

## Дополнительные IP и проверка маршрута

В карточке существующего AWG-сервера откройте **Manage tunnel** и выберите **AI services + TikTok (coverage settings below)**. Для избыточного покрытия в поле **Service IP coverage** выберите **Maximum coverage (shared CDN / cloud networks)** и нажмите **Save changes**. Удалять и заново создавать туннель или клиентов не требуется. При создании нового связанного сервера доступен такой же выбор.

**Maximum coverage** направляет через второй сервер также посторонние сайты и приложения, использующие включённые сети CDN и облачных провайдеров. Объём трафика через второй сервер может заметно вырасти. Это осознанное расширение маршрута для мобильных приложений, CDN и адресов из клиентского DNS-кэша, а не точное определение приложения по IP. Поле `upstream.service_ip_profile` хранит `standard` или `expanded`; у старых настроек без этого поля остаётся прежний профиль **Standard**. Переключение на другой режим маршрутизации сохраняет выбранный профиль; вернуться к стандартному покрытию можно в том же поле.

Расширенный пул включает опубликованные публичные IPv4-сети Cloudflare, Fastly, AWS, Google, Microsoft Azure, Oracle Cloud, а также объявления выбранных автономных систем ByteDance / TikTok, Akamai, CDN77, Gcore, DigitalOcean и Zenlayer. Для Akamai дополнительно используется опубликованный список CIDR. Это набор инфраструктуры общего назначения, а не утверждение, что каждый её адрес принадлежит ChatGPT, Claude или TikTok. Точные источники и сети записаны в `web-ui/data/expanded_service_networks.json`, загрузка и проверка — в `web-ui/service_networks.py`.

Снимок сетей включён в образ и доступен сразу, даже если источники недоступны. Для включённого расширенного профиля панель обновляет список в фоне раз в сутки; после ошибок повторяет попытку примерно через час. При отказе отдельного источника сохраняется его последний корректный список. На AWG обновление набора применяется атомарно. В расширенном профиле предварительно разрешённые адреса известных хостов также расширяются до соседней подсети `/24`; это помогает покрыть смену адресов внутри того же небольшого блока, но увеличивает число посторонних назначений в туннеле.

Поле **Additional service IPv4 addresses / networks** работает с обоими профилями и принимает по одному адресу или CIDR на строку; запятые также поддерживаются. Вносите только проверенные адреса назначения нужного сервиса. Изменение поля применяется после **Save changes**. Пустое поле удаляет ваши дополнения, сохраняя встроенные сети выбранного профиля и автоматическое определение. При переключении на другой режим список сохраняется для последующего возврата.

Дополнительная сеть направляет через второй сервер **весь** трафик к входящим в неё адресам. Не добавляйте целиком сеть общего CDN, если не хотите отправлять через Европу и посторонние сайты этого провайдера. Частные, служебные и слишком широкие сети отклоняются; допускается не более 256 записей публичного IPv4 с префиксом `/8` или уже. Обычный отдельный адрес сохраняется как `/32`.

Кнопка **Diagnostics** в том же окне проверяет сохранённые настройки. Без ввода проверяется `chatgpt.com`; можно ввести другой домен или конкретный публичный IPv4, с которым соединяется клиент. Показываются состояние туннеля, давность handshake, работа DNS, профиль покрытия, количество записей в наборах, счётчики совпадений и выбранный маршрут для каждого полученного адреса. Отдельно видны число успешно разрешённых известных хостов, общее число запросов, число ошибок, количество сохранённых адресов и время последней попытки и последнего получения адресов в UTC. Для расширенного пула показываются число сетей, ошибки и время обновления списков провайдеров. Последнее получение адресов может быть частично успешным — смотрите также число ошибок. Проверка не выводит закрытые ключи и не применяет несохранённые изменения формы.

Диагностика проверяет серверные правила, а не выполняет реальное соединение из приложения клиента. Если приложение использует защищённый DNS или старый кэш, проверьте **точный IP из его соединения**: адрес, определённый панелью по домену, может отличаться. При `fail_open` и неисправном туннеле даже распознанные сервисы выходят через первый сервер. Для проверки со стороны клиента закройте старое соединение приложения и создайте новое.

В профиле **Standard** обычный сайт **«мой IP» обычно показывает российский VPS**, если его адрес не совпал с адресом выбранного сервиса. В профиле **Maximum coverage** такой сайт тоже может выйти через Европу, если размещён в одной из включённых сетей. Ни один вариант сам по себе не доказывает маршрут ChatGPT или TikTok. Сопоставляйте результат диагностики конкретного назначения со счётчиками трафика при новом обращении клиента.

## Если второй сервер недоступен

- `fail_close`: трафик, которому положен туннель, блокируется. В режиме AI + TikTok прочие сервисы продолжают работать через первый сервер.
- `fail_open`: при обнаруженной неисправности трафик временно выходит через первый сервер; выбранные сервисы увидят его IP. После восстановления туннеля панель возвращает исходную политику.

Проверка доступности выполняется периодически. Отдельный запрещающий маршрут не позволяет выбранному трафику незаметно перейти на обычный маршрут, если выходной интерфейс пропал.

## Ограничения определения сервисов

- AWG передаёт IP-пакеты и сам не содержит доменных имён. Для надёжного изучения новых адресов клиент должен использовать обычный DNS через VPN. DoH, DoT, Android Private DNS, встроенный защищённый DNS браузера и приложения с собственным разрешением имён могут обойти классификацию. Предварительное заполнение и CIDR уменьшают зависимость от DNS клиента, но не устраняют это ограничение. При необходимости отключите защищённый DNS для этого подключения.
- После первого включения режима очистите DNS-кэш или переподключите клиент и перезапустите приложения: ранее закэшированный адрес мог ещё не попасть в набор маршрутизации.
- Один IP CDN может обслуживать несколько сайтов. После изучения адреса по DNS клиента, предварительного разрешения сервером или ручного добавления другой сайт на этом же IP тоже может выйти через туннель. Это ограничение маршрутизации AWG по адресам; накопление более широкого пула IP не делает определение приложения точнее.
- Новые домены, жёстко заданные IP и адреса, скрытые от DNS или sniffing, могут не распознаться. Поэтому `fail_close` защищает **распознанные назначения**, а не гарантирует распознавание любого будущего домена сервиса.
- В текущих профилях AWG туннелируется IPv4 (`AllowedIPs = 0.0.0.0/0`). DNS выборочного режима исключает AAAA-ответы; это не превращает профиль в полноценный IPv6 VPN. Если устройству нужна защита всего IPv6-трафика, настройте IPv6 отдельно либо отключите его для VPN-подключения.
- Выбор другого выхода не меняет правила самого сервиса, регион аккаунта, геолокацию устройства или другие сигналы, используемые TikTok и AI-сервисами.
- Максимальное покрытие тоже ограничено IPv4 и не гарантирует принятие адреса европейского VPS самим сервисом. Если нужный IP уже показывает `Route: upstream`, а приложение не работает, проверьте доступность сервиса через этот второй сервер, IPv6 на телефоне и состояние самого туннеля. Расширение пула не исправляет отказ сервиса принимать адрес или аккаунт.

## Установка и проверка

Обновление совместимо с предыдущими сохранёнными настройками. Версии AWG, ключи, клиентские профили и старый выбор российского сплита сохраняются; существующие серверы автоматически не переводятся на AWG 3 или новый режим маршрутизации.

В штатном `docker-compose.yml` данные находятся на хосте: `/etc/amnezia:/etc/amnezia` и `/etc/letsencrypt:/etc/letsencrypt`. Пересоздание контейнеров сохраняет эти данные, если оставить прежние подключения каталогов (или прежние тома при своей конфигурации), `.env` и опубликованные порты. Удалять каталоги данных, тома или заменять их пустыми не нужно. Во время пересоздания будет краткий перерыв соединений.

Если сервер стоит внутри вашей сети и использует свой Compose, сохраните его изменения: HTTP-порт управления `80`, прежние UDP-порты AWG, адреса, подключения каталогов и `.env`. Перед обновлением сделайте копию своего Compose и `.env` вне каталога проекта. Не заменяйте их штатным шаблоном и не используйте `git reset --hard` для обхода конфликта локальных настроек. Если `git pull` сообщает о конфликте, сначала совместите изменения, сохранив рабочие порты и каталоги. Отсутствие домена и HTTPS не требует изменения AWG-туннеля.

После получения изменений на сервере:

```sh
git pull --ff-only
docker compose up -d --build --force-recreate
```

Простой перезапуск старого образа не установит новые функции: нужен параметр `--build`. Сценарий обновления проверен в двух отдельных контейнерах с одним тестовым хранилищем: старая версия создала AWG 1/2/3, связанные серверы и VLESS, новая сохранила записи клиентов, ключи, файлы и экспортируемые профили и запустила прежние AWG-серверы. Повторяемый тест — `tests/awg_upgrade_smoke.py` (`create` со старым исходным кодом через `APP_SOURCE`, затем `verify` с новым). Тест предназначен только для пустого тестового хранилища.

Пересоберите образ: выборочному режиму AWG нужны `dnsmasq` с поддержкой ipset и утилита `ipset`. Нужны права `NET_ADMIN`; стандартный Compose уже предоставляет необходимые сетевые права. DNS-порт панели не требуется публиковать наружу.

```sh
docker compose build web-ui
docker compose up -d
python3 -m unittest discover -s tests -p 'test_*.py'
```

Для проверки настоящего сетевого пути используется `tests/awg_routing_smoke.py`. Запускайте её в отдельном тестовом Linux-контейнере с правами создания network namespace, `/dev/net/tun` и установленным образом проекта. Тест создаёт собственные изолированные пространства и временные ключи, проверяет AWG 2 и AWG 3, разные выходные IP-пути, DNS, изоляцию серверов, блокировку при отказе и удаление правил. Ему не нужен внешний интернет или рабочие конфиги.

```sh
docker run --rm --privileged --device /dev/net/tun \
  --mount type=bind,source="$PWD",target=/work,readonly \
  --entrypoint python3 amneziawg-web-ui:local \
  /work/tests/awg_routing_smoke.py
```

Отдельный `tests/awg_attach_smoke.py` проверяет изменение **работающего** сервера с настоящим AWG-клиентом. Для входа AWG 2 и AWG 3 он подключает выход AWG 2, заменяет его на AWG 3, меняет выборочный режим и отключает туннель. Проверяются неизменность ключей и файлов клиентов, отсутствие пересоздания входящего интерфейса, handshake и передача трафика после каждого изменения. Один запуск DNS намеренно завершается ошибкой для проверки восстановления прежнего туннеля.

```sh
docker run --rm --privileged --device /dev/net/tun \
  --mount type=bind,source="$PWD",target=/work,readonly \
  --mount type=bind,source="$PWD/scripts",target=/app/scripts,readonly \
  --entrypoint python3 amneziawg-web-ui:local \
  /work/tests/awg_attach_smoke.py
```

Обе проверки пройдены в отдельном Linux-контейнере при разработке. Они подтверждают сетевую логику на контролируемых адресах; доступность внешних AI-сервисов и TikTok нужно дополнительно проверить через выбранный вами второй сервер.

Новый режим проверяется отдельно в `tests/domain_routing_smoke.py`: настоящий AWG 2/3 выход, одинаковый IP у выбранного сервиса и YouTube, HTTP/TLS, DNS TCP/UDP, FakeIP для непрозрачного TCP/UDP, перезапуск и аварийная остановка процесса, смена выбора, fail-close/fail-open и изоляция входящих серверов. Тест использует публичный тестовый сертификат из `tests/fixtures`; его ключ не предназначен для рабочих серверов.

```sh
docker run --rm --privileged --device /dev/net/tun \
  --mount type=bind,source="$PWD",target=/work,readonly \
  --entrypoint python3 amneziawg-web-ui:local \
  /work/tests/domain_routing_smoke.py
```

Для диагностики внутри контейнера полезны `awg show`, `ip rule show`, `ip route show table <table_id>`, `ipset list awgsel_<table_id>`, `ipset list awgpool_<table_id>`, `ipset list awgwide_<table_id>` и счётчики правил `iptables -t mangle -L -n -v`. Первый набор содержит адреса, изученные по клиентскому DNS, второй — предварительно найденные адреса и сети сервисов, третий — широкие сети провайдеров и существует только при расширенном покрытии. После DNS-запроса выбранного сервиса его IPv4 должен появиться в первом наборе. Не публикуйте полный вывод конфигураций или дампов AWG: они могут содержать секреты; встроенная диагностика возвращает только предусмотренные поля.
